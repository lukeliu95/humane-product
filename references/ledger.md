# 台账怎么记

`docs/product/LEDGER.md` 是这个产品的"记性"：每轮开发前读，每次评审后写。目的是让下一轮的 AI 不再犯同样的错，也不把否决过的方向又做一遍。

模板在 `templates/LEDGER.md`。

## 规矩

- 只追加不删。作废的条目用删除线，写上作废的原因和日期。
- 每条写日期和"谁定的"。模型的建议不算定了，负责人确认了才算。
- 用户看得到的叫法以术语表为准，代码里的变量名不受限制。

## 六块

| 块 | 写什么 |
|---|---|
| 上限 | 主按钮、筛选条件、步数等上限，以及改动的理由 |
| 术语表 | 用户的叫法、界面统一用什么、不要用哪些词（`smell_scan.py --ledger` 会按"不要用"一列扫源码） |
| 不做清单 | 不做什么、为什么 |
| 否决记录 | 被否决的方案、理由、**什么情况下可以重新考虑**（防止旧方向反复回来，也防止永远回不来） |
| 待议 | 开发中冒出来、还没批准的想法；批准前不写代码 |
| 产品级规则 | 从评审里提炼出来、对整个产品都成立的规则 |

## 评审结论怎么写回

先问一句：这条只对这一处成立，还是对整个产品都成立？

- 只对这一处：直接改掉，不进台账。
- 对整个产品：写成一条规则进"产品级规则"。例：不写"申请列表的删除要能撤销"，写"所有删除都给撤销"。

## 待议项怎么收尾

交付时把待议项列给负责人：
- 要做：写进意图卡的变更记录，下一轮做
- 不做：移进不做清单，写理由

## 反哺本 skill

一条规则在两个以上的产品里都成立，就向这个 skill 的维护者提议把它加进 interaction-smell.md（提 issue 或 PR）。只提议，不直接改 skill。
